The problem

Compaction keeps a summary and drops the transcript. What it drops includes the operator's own words — the prompt the work was commissioned with, and every correction since.

Before

The record rode inside a normal turn — one injected user-role message competing with the compaction summary and the full system prompt.

The turn most likely to resume the wrong task, confidently.

After

The record gets its own dedicated initialization step. That step carries the record and one instruction, and nothing else.

The operator's prompt waits until the acknowledgement lands.

The three phases

Phase A
CODE — never a model
Render the record and write it to the session's own state directory. compaction-[id]-[session-id].md
→
Phase B
THE INITIALIZATION STEP
The step carries the record plus one instruction. No system prompt. No other injections. reply with nothing but OK
→
Phase C
ACKNOWLEDGEMENT, THEN THE REAL TURN
OK is absorbed and folded as a log event, so it survives a resume. The deferred prompt and normal injections then proceed. a non-OK reply is logged, never fatal

Why Phase A is code. Selection and rendering are pure and total, so the record is reproducible and costs no model call. Selecting the event window is the only decision it makes, and that decision is stated once, in selectCompactionEvents.

The selection rule

The window starts at the newest turn-starting prompt — that prompt restates the task, and what came before it is the previous turn's work, which the summary already covers. The cap then trims the window's oldest end, so a long run keeps the newest events.

Turn-starting prompts are included in full from the whole session. Steering input is not.

Phase B — the initialization step

Two hooks, both registered on the agent, both in the fork-owned package.

1 · agent/pre-step — own the exchange

ctx.on('agent/pre-step', async ({ agent, messages, signal }, next) => {
  const base = await next()
  if (base.kind === 'reject') return base
  const session = agent.session
  const state = ctx.sessionProjections.stateOf(session, 'sessionRecovery')

  // Past the acknowledgement: admit the messages this plugin deferred for the
  // real turn, then let the ordinary injections run.
  const stashed = deferred.get(session)
  if (stashed !== undefined && !awaitingAcknowledgement(state)) {
    deferred.delete(session)
    return { ...base, messages: [...stashed, ...base.messages] }
  }
  // Nothing to answer: no compaction yet, or this compaction already answered.
  if (state.compactionSeq === null || state.recoverySentSeq === state.compactionSeq) return base

  await writeCompactionLog(root, session, state, compactionEvents)
  const path = compactionLogPath(root, session, state.compactionId ?? String(state.compactionSeq))
  const record = await readRecord(path)
  // … builds the context message and defers the operator prompt …
})

2 · system-prompt/assemble — empty the prompt for that step

// The initialization step carries no system prompt and no other injections.
ctx.on('system-prompt/assemble', async (assembly, context, next) => {
  const agent = context.agent
  if (agent === undefined) return next()
  const state = ctx.sessionProjections.stateOf(agent.session, 'sessionRecovery')
  if (!awaitingAcknowledgement(state)) return next()
  return { sections: [], contexts: [], tools: assembly.tools, variables: assembly.variables }
}, { prepend: true })

The gate both hooks share

export function awaitingAcknowledgement(state: SessionRecoveryProjection): boolean {
  return state.compactionSeq !== null && state.compactionSeq !== state.absorbedSeq
}

Why the system prompt can be emptied

This was the design's riskiest assumption, and it is checkable in upstream source rather than by experiment.

system-prompt/assemble

Returns the waterfall value verbatim unless a section declaring complete: true was registered.

harness:identity is registered as a plain section — no complete.

So an emptied assembly is genuinely empty

The only complete: true registrations in the repo are in tests plus packages/skill/tool-skill/src/index.ts.

None of them is the harness identity or the persona.

And it avoids a Tier-2 edit entirely. Because the waterfall is public API and the listener is registered on the agent scope, the whole mechanism lives in the fork-owned plugin. That is why Tier-2 stays at 138 files.

An earlier round proposed blanking the prompt via agent/request. That is impossible: LlmCallConfig carries only provider, model, reasoning effort, and sampling scalars — the system prompt is not in it.

Tests — 17 passing

Extended tests/session-recovery-context.spec.ts. The names are the specification:

Compaction initialization

  • contributes nothing to a session that was never compacted
  • carries the record and one instruction, and nothing else
  • writes the record to compaction-[id]-[session-id].md
  • admits the operator prompt only after the acknowledgement
  • carries the recovered prompt once the acknowledgement is folded
  • leaves a rejected step rejected
  • suppresses the system prompt for exactly the recovery step
  • reports an awaiting compaction until the acknowledgement lands

Selection & rendering

  • keeps everything after the newest prompt
  • keeps the newest events when the window is longer than the cap
  • keeps the whole window when it fits the cap

renderCompactionLog

  • names the session, the summary, the prompts, and the events
  • says so plainly when there is nothing to show

Filename

  • is compaction-[id]-[session-id].md

The three that matter most: “and nothing else”, “only after the acknowledgement”, and “for exactly the recovery step”. Those are the design's claims, stated as assertions.
