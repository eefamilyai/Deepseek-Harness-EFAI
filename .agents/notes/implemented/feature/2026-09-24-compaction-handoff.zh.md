# Agent Note: Compaction hands off in the same step, from a code-kept ledger

Status: implemented

[English](2026-09-24-compaction-handoff.md) | 中文

## 问题

压缩（compaction）之后，模型经常接错任务，或者干脆停下。只阅读源码、不查看任何会话，就找到了五个相互叠加的原因。

1. **恢复花掉了一步。** `session-recovery-context` 用一个"确认记录"的步骤来应答压缩。回复中不调用任何工具的一步会结束轮次（`packages/core/agent-loop/src/agent.ts`），因此每个在运行中途被压缩的任务都停在那里，操作者的消息要等到下一轮。
2. **保留下来的只是模型写的东西。** 检查点是模型的转述。它丢掉的恰恰是代码可以确切知道的内容：操作者的原话、之后的纠正、改过的文件、仍未解决的错误、待办清单。先前的恢复消息携带的是提示词和原始事件尾部，而不是工作的状态。
3. **在 `ds_direct` 上，重新预热丢掉了检查点。** 压缩会打开一个新的 DeepSeek 网页对话，并在一个 48,000 字符的提示里预热它。光是系统提示——二十多个工具的工具协议——就占去大半，而检查点作为最旧的一轮没有被固定（pin）。sidecar 自己针对 `kind: "compact"` 的固定规则匹配不到适配器发送的任何内容。
4. **摘要器只看到最新的一端。** `ds_direct` 上大于一个受限提示的摘要请求会从最旧处开始裁剪，因此较早的工作根本没有被总结。
5. **系统提示每轮存一次。** `ds_direct` 在每个串接的轮次都重新发送它。网页对话保留收到的每一个提示，因此服务器端的对话早在工作内容填满之前，就被工具协议的副本填满了。

## 决定

代码保留代码能知道的内容，恢复从不打断它所恢复的工作。

- **从日志折叠出的账本**（`session-recovery-context`，`src/ledger.ts`）。一个 Session 投影逐字记录操作者消息（达到上限时保留第一条和最新的几条）、轮次中途的纠正、创建、编辑与读取过的文件、最近的命令及其结果、未解决的错误（同一工具在同一目标上的后续成功会将其消解）、待办清单，以及最新的检查点。
- **同一步里的交接。** 一个以 prepend 方式注册的 `agent/pre-step` 监听器先让链运行——压缩就在其中运行——当最新检查点尚无交接时，把一条消息放在该步最前面。交接消息包含请求、状态、最近改动文件的当前内容、`git status`、完整记录的路径，最后是"Continue from here"：检查点的 Current Work 与 Next Step、进行中的待办，以及最新的请求。它告诉模型不要确认或复述它，也从不重述检查点。其预算是路由窗口的一个比例。每次压缩都有一个记录文件把交接与检查点保存在磁盘上。
- **一行焦点提示**：第一次压缩之后，运行时上下文中的一行让进行中的待办和下一步留在模型最近的注意力里，就像会重写自己待办文件的智能体借此让目标始终在视野中。
- **Kiln 上的固定与折叠**（`llm-kiln`）。`compact-checkpoint` 与 `session-recovery` 两类轮次被固定，重新预热从不裁掉它们。`ds_direct` 上大到一个受限提示装不下的摘要请求会分段折叠，每段都把累积摘要放在上游摘要器本就会合并的 `<compacted-summary>` 标签中。
- **每个对话一份系统提示**（`ds_direct.py`）。它在对话打开或重新预热时、内容变化时、以及每 `KILN_DS_SYSTEM_EVERY` 轮（默认 8）发送；其他轮次只附一行说明，且只有真正发送时提示预算才为系统提示付费。
- **压缩之前的观察遮蔽**（`output-masking`，新增）。当路由窗口使用过半时，旧的、大的、成功的工具结果会通过工具结果修剪器自己的替换协议被一次性批量变为一行存根，使压缩更晚触发、需要总结的内容更少。

这一设计遵循已发表的做法。JetBrains Research 发现，在 SWE-bench 智能体上，观察遮蔽与 LLM 摘要效果相当，成本约为一半。Factory 对压缩的评估发现，锚定于先前摘要的结构化摘要保留得最多，而文件与产物的轨迹是每种方法最先丢失的内容。Claude Code 在压缩后重新附上最近读取的文件，并告诉模型直接继续、不要确认摘要。Codex 为下一个上下文写一份交接，并逐字携带用户最近的消息。Manus 把错误留在上下文里，把文件系统当作记忆，并复述待办清单以保持目标在注意力中。

## 考虑过的替代方案

**只改进摘要提示。** 上游的检查点已有 Current Work 与 Next Step 两节；它缺的是确定性。没有任何提示能让模型可靠地复现逐字请求、文件清单或未解决的错误，读者也无法核实它是否做到了。

**保留确认步骤，但把它标记为轮次中途。** 回复不调用工具即结束轮次是上游的规则，而且承重。任何额外的一步要么结束轮次，要么需要修改 agent-loop，而冻结的接缝禁止这样做。

**像以前一样重新注入整段事件尾部。** 尾部是最近发生的事，不是重要的事：它把预算花在例行调用上，而仍然遗漏任务说明、文件清单和更早的错误。

**在 `ds_direct` 上改走付费路由做摘要。** 这能绕开受限提示，但会让压缩依赖一个免费路由本就要避免的密钥。折叠让该路由保持自给自足。

**持续逐条遮蔽。** 每次遮蔽都会从被遮蔽节点起改写提示前缀。在使用量阈值处成批遮蔽，让这种缓存失效很少发生，而且只为实际的节省而发生。

## 后果

被压缩的轮次在被压缩的那一步里继续进行。模型从日志本身看到自己被要求做什么、工作的确切状态，并在续接位置结束阅读。每次压缩增加一条持久的交接事件和一个记录文件。

账本的工具知识按名称识别：新的文件或 shell 工具会被记为一次调用，但在账本学会它之前不会增添文件或命令。被遮蔽的输出必须通过重新运行调用来重新生成，而有副作用的调用会返回不同的内容。在 `ds_direct` 上，长对话的摘要每段花费一次调用。

账本中的操作者消息是会话自己的文本，因此交接会携带操作者写下的任何内容。与它所读取的日志一样，它留在会话内部。
